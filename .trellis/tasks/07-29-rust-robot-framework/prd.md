# Design Rust robot framework

## Goal

定义一套可扩展、可观测、可实施的机器人软件总体框架，使设备接入、节点通信、实时控制、任务编排和安全停止具有清晰边界；在 Orange Pi 5 Plus 上以达妙 DM-J4310-2EC 建立首个真实硬件闭环，并以 RK3588 作为首个性能验收平台。

## Background

目标系统采用五个关注面：

1. 底层通信与设备驱动层。
2. 基于 Zenoh 和 Protocol Buffers 的中间通信层。
3. 底盘、机械臂、视觉等算法与应用层。
4. 贯穿所有层级的监控与数据记录能力。
5. 位于顶层、负责安全生命周期与自动任务编排的 FSM/逻辑编排层。

## Decision Baseline

- 以下带编号要求是本规划的唯一决策基线。源码依赖只有一条合法主路径：`上层 -> 中间层 -> 底层`；进程可以组合多层，但只能承担装配职责，不能借此绕过中间层契约。

## Requirements

- R1：框架必须定义通信适配器与设备驱动的边界，使 CAN、USB 和后续传输方式可以独立扩展。
- R2：框架必须定义电机、IMU、摄像头、雷达和通用传感器的稳定设备接口及生命周期。
- R3：底层传输、设备驱动、设备协议与中间层必须全部由 Rust 实现和维护。
- R4：中间层必须把设备数据与控制能力映射为基于 Zenoh 的通信接口，并使用 Protocol Buffers 定义跨边界数据契约。
- R5：算法与应用层必须能够通过统一接口消费传感器数据、发布控制结果，而不依赖具体 CAN/USB 驱动实现。
- R6：框架必须允许底盘、机械臂、视觉及后续算法模块独立部署、替换和演进。
- R7：可观测能力必须贯穿驱动、中间件、算法应用与 FSM，包括健康状态、故障信息、关键指标、日志和可配置的数据记录。
- R8：FSM 必须能够表达任务编排、状态转换、超时、失败处理以及对各层运行状态的协调。
- R9：总体设计必须明确各层职责、进程/组件边界、数据流、控制流、错误模型、配置方式和扩展点。
- R10：规划必须给出分阶段实施顺序和每阶段可验证的交付标准。
- R11：首个部署、实时性和性能验收基线必须使用 RK3588；架构仍需隔离板级实现，以便后续适配 RDK X5。
- R12：CAN 适配必须以 Linux SocketCAN 语义作为优先边界；若板载 CAN 不能直接暴露为 SocketCAN，则通过独立传输适配器接入。
- R13：硬件配置必须以带版本和校验规则的 YAML 文件完成构型选择与设备绑定；首版范围限于机械臂构型及电机 ID、IMU 通信方式及波特率、底盘构型及电机 ID。
- R14：同一控制接口必须支持舵轮、麦克纳姆轮和全向轮底盘，但各底盘运动学与约束应保持为可替换模块。
- R15：IMU 和摄像头驱动必须分别允许 USB/UART 与 USB/MIPI 后端，而不改变其上层数据契约。
- R16：底盘控制必须包含基于 IMU 反馈的闭环能力，并为运动跟踪提供状态估计输入。
- R17：核心业务层必须保持 `底层 <- 中间层 <- 上层` 的单向依赖图；下层不得导入上层模块，中间层不得绕过底层抽象，上层不得直接访问底层驱动。
- R18：底层只负责传输、设备生命周期、原始/标准化设备数据与单设备命令，不负责机器人级运动闭环。
- R19：中间层只负责把底层能力映射为 Zenoh/Protobuf 通信接口及必要的协议适配，不承载底盘算法或任务业务逻辑。
- R20：上层负责底盘运动学、轮组协调、轮速与 IMU 融合、速度/航向闭环以及后续轨迹跟踪。
- R21：监控与 FSM 的实现不得产生跨层或反向业务依赖；各层只能通过其合法边界暴露健康状态、事件、命令与状态转换输入。
- R22：系统必须为底盘、机械臂和时间敏感算法提供低延迟、低抖动的控制路径，并明确实时线程、CPU 调度、内存分配和阻塞 I/O 约束。
- R23：目标部署必须支持带实时补丁的 Linux，并将实时性要求落实为可测量的周期、截止期限、最坏抖动和超时行为，而不是仅以平均延迟衡量。
- R24：FSM 必须保持最小硬件耦合与最小资源占用，通过稳定的中间层契约编排上层能力，并能够监督进程健康和触发安全状态。
- R25：规划阶段必须调研并比较适合 ARM Linux 实时机器人系统的进程划分、线程调度、进程监督和 FSM 实现方式。
- R26：同进程的驱动 I/O 与实时算法必须使用独立线程，并通过有界、预分配、具有明确溢出策略的通道或最新值邮箱交换数据。
- R27：设备 I/O 线程必须只执行采集、时间戳、轻量校验和命令收发，不得执行视觉、机械臂、底盘运动学或其他耗时算法。
- R28：实时路径必须避免无界队列、不可控阻塞、运行期非必要内存分配以及在高优先级线程中执行日志落盘或网络重连。
- R29：上层无论与设备驱动同进程还是跨进程部署，都必须只依赖中间层公开的数据与控制接口。
- R30：同进程快速路径必须由中间层封装，并与 Zenoh/Protobuf 外部契约保持相同的消息语义、时间戳、序列号和错误模型。
- R31：同进程实时通信机制必须根据 ARM 目标板上的延迟、抖动、CPU、内存、背压与故障隔离测试结果选择；优先采用预分配、单写单读或最新值语义，不得仅凭理论选择。
- R32：跨进程和跨节点通信必须使用 Zenoh + Protobuf；需要被监控或记录的实时数据由中间层按策略镜像到该通信面。
- R33：设备帧解析、校验、单位换算和控制命令编码必须由经过测试的 Rust 驱动实现，不得由 YAML 动态解释。
- R34：YAML 配置模型应参考 `rm_control`，但只保留本系统实际需要的选择项，避免把运行期参数和协议实现细节全部配置化。
- R35：`motion-rt` 必须成为运动总线的唯一调度域，并隔离设备 I/O、底盘控制和机械臂控制线程。
- R36：`perception` 必须与 `motion-rt` 进程隔离；本地摄像头路径在平台支持时优先使用 V4L2/DMABUF 等缓冲区句柄机制减少图像复制。
- R37：`robot-fsm` 只通过中间层状态/命令契约编排任务与安全状态，不得直接持有硬件、执行运动学或承担高带宽数据处理。
- R38：`telemetry-recorder` 必须支持背压、降采样和丢弃策略，任何磁盘或压缩阻塞不得反向传播到实时发布者。
- R39：各进程必须作为独立系统服务接受 systemd 的启动顺序、权限、重启策略和 watchdog 监督；机器人 FSM 不作为通用进程管理器。
- R40：物理急停必须能够绕过 Linux、Zenoh 和 FSM，直接切断电机使能或动力输出，并向软件提供可观测状态。
- R41：电机驱动器必须配置通信超时保护；命令租约过期时必须由驱动器独立进入零输出、制动或失能的预定义安全状态。
- R42：`motion-rt` 必须监测控制命令、设备反馈、IMU 数据和自身周期截止期限；任一关键输入超时都必须触发分级安全停止。
- R43：FSM 负责协调任务中止、能力降级和安全状态传播，但不得成为急停或驱动器失能的唯一执行者。
- R44：`motion-rt` 必须以 1 kHz 为首选基准周期，并允许在启动前选择经验证的 500 Hz 降级配置；运行时不得静默改变控制周期。
- R45：CAN 调度器必须根据帧长度、总线速率、节点数量、协议分组能力和反馈频率计算总线预算，经典 CAN 的计划利用率默认不得超过 70%。
- R46：设备接收采用事件驱动；控制与发送任务按各自周期调度，禁止用单一 1 kHz 轮询假设覆盖所有设备。
- R47：首版频率目标为底盘速度/姿态闭环 500–1000 Hz、里程计/状态估计 200–500 Hz、轨迹跟踪 50–200 Hz；每项必须具有时间戳、截止期限和陈旧数据策略。
- R48：实时验收必须在 CPU、NPU、网络和磁盘并发压力下测量最大唤醒抖动、执行时间和截止期限丢失；初始目标为最大唤醒抖动不超过 100 μs且持续测试无丢期。
- R49：FSM 顶层至少包含启动、待机、使能、运行、降级、故障、急停和关机语义；具体任务应作为运行态下的子状态，而非扩散为不可维护的平面状态集合。
- R50：FSM 的状态、事件、守卫和转换必须在 Rust 代码中静态定义，并能够生成或导出用于评审的状态图与转换表。
- R51：FSM 事件处理必须确定且串行化；同一初始状态和同一有序事件序列必须得到相同的状态与命令输出。
- R52：每个对外动作必须具有命令标识、确认、超时、取消和幂等策略；FSM 不得把“消息已发布”等同于“动作已完成”。
- R53：FSM 验证必须覆盖状态可达性、终止/安全状态可达性、非法转换、重复/乱序/陈旧事件、守卫边界、超时、组件失联和急停抢占。
- R54：FSM 库选型必须通过最小原型验证层次状态、无阻塞事件处理、可观测转换、资源上限与测试能力，不得仅因库提供宏而直接采用。
- R55：FSM 启动时必须忽略任何持久化的活动状态，主动发布运动禁止，并从实时观测重建系统能力视图。
- R56：恢复期间遇到未知状态、组件状态冲突、关键组件失联或查询超时，必须进入 `Fault`，不得猜测或沿用崩溃前状态。
- R57：事件日志和任务检查点仅用于诊断与人工辅助恢复；未经重新健康检查和显式使能，不得据此自动产生运动命令。
- R58：各进程必须通过非阻塞的结构化诊断接口产生日志、指标和追踪关联信息；实时线程只写入有界缓冲，不得直接执行格式化、网络导出或磁盘 I/O。
- R59：`telemetry-recorder` 必须以 MCAP 记录 Protobuf schema、通道、发布时间、记录时间和序列号，并生成支持按时间与通道查询的索引。
- R60：控制、IMU、里程计、FSM、健康与故障通道必须持续记录；高带宽原始图像/点云必须默认采用有界滚动缓存和触发式保存。
- R61：记录系统必须具有数据优先级、降采样、保留期限、磁盘配额和磁盘写满策略；资源不足时先丢弃可重建的大带宽数据，不得阻塞实时生产者。
- R62：OpenTelemetry 只能作为可替换的外部导出适配器，核心监控接口不得绑定其当前 Rust SDK 或远端 Collector 的可用性。
- R63：底层传输、设备驱动和设备协议实现不得包含 C/C++/Python 业务实现；厂商内核驱动或不可替代的系统库若必须使用 FFI，必须被 Rust 安全封装并经过单独风险审查。
- R64：中间层的进程内通道、Zenoh 适配、Protobuf 契约、健康/命令语义和桥接逻辑必须使用 Rust。
- R65：`motion-rt` 和 `robot-fsm` 不得嵌入 Python 解释器或加载非 Rust 算法插件；非 Rust 上层模块必须作为可独立崩溃和重启的进程运行。
- R66：Protobuf 构建必须能为 Rust、C++ 和 Python 生成兼容数据类型，且跨语言实现必须通过同一套契约测试。
- R67：ROS 2 兼容必须由独立 `ros2-bridge` 进程提供，在核心 Protobuf 契约与 ROS 2 topic/service/action 之间执行显式、版本化映射。
- R68：`ros2-bridge` 的缺失、崩溃、重启或 DDS 故障不得影响 `motion-rt`、设备驱动或 FSM 的本地安全行为。
- R69：ROS 2 桥接不得向 ROS 2 暴露绕过中间层的底层驱动句柄；MoveIt 2、Nav2 和其他 ROS 2 应用只作为上层客户端。
- R70：若采用官方 `zenoh-bridge-ros2dds`，首版优先部署独立可执行程序而非加载进核心 `zenohd` 的动态插件，并锁定兼容版本。
- R71：Zenoh 必须支持通过以太网连接本机外进程或计算节点；网络断开、恢复和抖动不得破坏本地安全闭环。
- R72：首版网络配置可以使用可信局域网内的非加密传输，但消息契约和 key expression 不得依赖单机地址或阻止后续加入认证与访问控制。
- R73：底层首版不提供通用 TCP/UDP 网络设备传输接口；若后续接入网口雷达、相机或控制器，应作为独立扩展任务加入底层。
- R74：Zenoh/Protobuf 契约必须允许网口节点发布与本地中间层相同语义的传感器状态、控制命令和算法结果，不得按本机/远端来源设计不同业务接口。
- R75：所有可能影响运动的网络输入必须携带源时间戳、接收时间戳、序列号、来源标识、会话 epoch、有效期和质量/同步状态，并在消费前执行陈旧、乱序和租约校验。
- R76：系统必须按通信路径声明实时等级与降级行为；未经过最坏时延和时钟同步验证的普通以太网输入不得宣称满足 1 kHz 硬截止期限。
- R77：架构必须为后续 PTP、硬件时间戳、TSN 或其他确定性网络扩展保留时钟质量与链路能力字段，但首版不强制实现这些网络能力。
- R78：网口输入参与控制时，`motion-rt` 必须以非阻塞快照读取最新有效样本；本周期无新数据时不得等待网络或 Zenoh executor。
- R79：每类网口传感器或指令必须定义最大年龄、丢失容忍、替代来源和安全降级策略；超出有效期的数据必须显式拒绝。
- R80：首版不得将普通以太网路径计入 1 ms 硬实时保证；其端到端延迟、抖动和丢包应作为软实时指标独立监控。
- R81：底盘算法必须为三类构型提供统一的车体速度与 SE(2) 轨迹接口，同时将具体运动学、转向约束和轮组分配保持为可替换模块。
- R82：底盘状态估计必须融合轮组反馈与 IMU，并允许通过中间层接收外部位姿修正；每种输入都必须携带时间戳、协方差/质量和陈旧状态。
- R83：首版底盘闭环必须包含车体速度、航向保持和轨迹跟踪，但不得把 SLAM、地图管理或全局路径规划实现进 `motion-rt`。
- R84：自动项目逻辑编排器必须作为 FSM `Running` 层次下的受控执行器；FSM 仍拥有使能、急停、故障、降级和取消的最终优先级。
- R85：逻辑积木至少应能表达动作、顺序、条件选择、并行、超时、重试、循环、守卫和取消，并允许复用为更高层子流程。
- R86：每个叶子动作只能通过中间层发出带确认和取消语义的命令，不得直接访问驱动或在 FSM 事件线程执行长耗时工作。
- R87：编排器必须把完成、失败、超时和取消结果确定地反馈给 FSM；急停或故障必须能够抢占并取消整个活动任务树/图。
- R88：HSM 与任务编排器必须分离职责：HSM 管理生命周期与安全不变量，任务编排器只在合法 `Running` 子状态内执行自动项目。
- R89：首版任务定义必须使用类型化 Rust DSL 构建，并编译为可验证的内部表示；任务节点必须具有稳定 ID、输入/输出类型、资源声明和取消语义。
- R90：未来任何图形化或 YAML 编排前端只能生成相同任务 IR，并通过同一结构、资源和安全校验，不得引入第二套执行语义。
- R91：所有运动命令必须包含资源、所有者、租约 ID、会话 epoch、序列号和截止时间；缺少或不匹配当前授权的命令必须被拒绝。
- R92：FSM 必须对每个独占资源维护单一活动租约，支持授予、续租、主动释放、超时撤销和高优先级抢占，并记录完整审计事件。
- R93：`motion-rt` 必须独立缓存当前有效授权并在每周期校验；FSM 崩溃、断网、epoch 变化或租约超时不得保留运动权限。
- R94：人工接管和故障抢占必须先使旧控制者失效，再授权新控制者；陈旧控制命令在重连后不得重新生效。
- R95：资源所有权可以按底盘、机械臂等边界分别授予，但并行授权必须通过任务资源冲突校验和 FSM 安全守卫。
- R96：首个具体电机驱动必须面向达妙电机，以 Rust 实现 CAN 协议、生命周期、命令、反馈、故障和通信超时处理。
- R97：首个集成里程碑必须以真实达妙电机完成从 SocketCAN 驱动、中间层接口、上层控制、监控记录到 FSM 使能/停机的闭环验证。
- R98：DM-J4310-2EC 首版驱动必须支持 MIT 命令、使能、失能、故障复位、位置/速度/转矩/温度反馈，并在失能启动阶段读取和验证 ESC_ID、MST_ID、CTRL_MODE、CAN 超时以及 PMAX/VMAX/TMAX；普通启动不得自动写入或持久化电机参数。
- R99：MIT 帧编码规则与增益量程必须在 Rust 类型中静态定义并进行边界测试；位置、速度和转矩量程必须读取电机运行时寄存器、通过类型化安全策略约束并在使能前完成验证，不得由机器人 YAML 覆盖，也不得把单个 SDK 型号预设当作通用产品事实。
- R100：所有首版实时周期、抖动、CPU、内存、Zenoh、记录和压力测试结果必须记录具体 RK3588 载板、内核、实时补丁、设备树、频率调节器和散热条件。
- R101：Orange Pi 5 Plus 板级适配必须管理 CAN 设备树 overlay、SocketCAN bring-up、CAN 收发器连接、IRQ/CPU 亲和性、频率调节器和温控配置，并与通用 RK3588 逻辑隔离。
- R102：部署基线必须固定 Ubuntu 22.04 Server、Orange Pi/Rockchip 5.10 BSP 源码版本、对应 PREEMPT_RT 补丁版本和可复现内核配置。
- R103：BSP 与 PREEMPT_RT 的合并冲突、第三方驱动行为和后续安全维护风险必须记录；任何内核或设备树升级都必须重新执行完整实时与硬件回归。
- R104：通信层设计必须以固定提交源码审阅 Horus 的核心绑定、共享内存和进程队列实现，并在 RK3588 上复现实测；不得直接采用其性能宣传、首个可用核心语义或以 `needs_drop` 自动判断共享内存 POD 安全。
- R105：本地跨进程快速路径必须使用显式安全布局契约、版本化共享内存、有界容量、缓存行隔离、撕裂检测、崩溃端点回收、明确溢出语义和丢弃计数；实现仍归中间层所有，上层不得直接打开共享内存或绕过中间层。

## Acceptance Criteria

- [ ] PRD 明确系统目标、范围、约束和可验证要求。
- [ ] 技术设计覆盖五层架构、组件边界、典型数据流与控制流。
- [ ] 技术设计给出 Rust crate/workspace 的建议拆分及稳定接口原则。
- [ ] 技术设计定义 Zenoh key expression、发布/订阅、查询/应答及命令确认的使用边界。
- [ ] 技术设计定义 Protobuf schema 的组织、版本兼容和生成策略。
- [ ] 技术设计覆盖监控、故障传播、记录与回放方案。
- [ ] 技术设计覆盖 FSM 的任务模型、状态归属、异常/超时和安全降级策略。
- [ ] 实施计划能够按阶段构建和验证最小闭环，并标注高风险决策与验证方式。
- [ ] 一份 YAML 机器人描述能够选择机械臂构型及其电机 ID、IMU 通信方式及波特率、底盘构型及其电机 ID，并在启动时完成结构化校验。
- [ ] YAML 中不存在 CAN 帧布局、字节序、校验算法或任意表达式等协议解释能力。
- [ ] 相同的上层速度/运动命令可以驱动舵轮、麦克纳姆轮或全向轮运动学模块，而不修改驱动与通信层接口。
- [ ] CAN 电机、USB/UART IMU 和 USB/MIPI 摄像头均具有明确的可替换后端边界。
- [ ] 设计明确 IMU 参与底盘闭环和跟踪时的数据流、频率、时间戳及失效行为。
- [ ] 构建期可以检查并证明核心 crate 依赖图只允许 `上层 → 中间层 → 底层`，不存在上层直连底层、反向依赖或借助配置/监控/测试辅助 crate 建立的旁路。
- [ ] 底层和中间层代码中不存在底盘运动学、航向闭环、轨迹跟踪或任务状态逻辑。
- [ ] 上层只通过中间层公开的数据和控制契约完成底盘闭环，不导入具体 CAN、UART、USB 或摄像头后端。
- [ ] 设计为实时控制路径定义目标周期、截止期限、最坏允许抖动、线程优先级关系以及禁止出现在实时线程中的操作。
- [ ] 设计说明视觉与机械臂算法如何低延迟使用控制能力，同时证明不会阻塞设备 I/O 或破坏层级依赖。
- [ ] FSM 进程设计具有明确的职责、资源预算、健康监督、崩溃恢复和安全降级方案，并引用调研依据。
- [ ] 同一进程内能够独立配置驱动 I/O、控制算法和非实时任务的线程优先级与 CPU 亲和性。
- [ ] 压力测试下，算法超时或阻塞不会阻止 CAN/IMU I/O 线程继续收发与更新时间戳。
- [ ] 架构检查证明机械臂、视觉和底盘模块均未直接依赖底层 crate，即使它们与驱动链接在同一进程中。
- [ ] 在 RK3588 上对候选进程内通道完成延迟、最坏抖动、CPU、内存和过载行为基准测试，并据此确定实现；RDK X5 留作后续复验。
- [ ] 视觉进程崩溃、重启或内存压力不会终止 `motion-rt`，并能被 FSM 感知为能力降级。
- [ ] 记录进程停止消费或磁盘写满时，实时控制仍满足其截止期限，且系统产生明确告警。
- [ ] systemd 能检测各进程崩溃或 watchdog 超时并按策略恢复；FSM 状态机不会承担服务拉起逻辑。
- [ ] 断开 Zenoh、挂起 FSM 或终止 `motion-rt` 时，驱动器仍能在规定超时时间内独立停止输出。
- [ ] 触发物理急停时，无论软件处于何种状态都能切断运动输出，并在软件恢复后要求显式复位而不是自动恢复运动。
- [ ] 对命令陈旧、IMU 陈旧、电机反馈丢失和控制周期超时均有故障注入测试及确定的安全状态。
- [ ] 1 kHz 配置在目标板压力测试中满足 1 ms 截止期限和 100 μs 最大唤醒抖动目标，或测试结果明确触发经验证的 500 Hz 配置。
- [ ] 启动前能够检测 CAN 配置是否超过 70% 计划利用率，并拒绝不安全配置或给出明确的降频结果。
- [ ] 运行时监控分别报告唤醒抖动、单周期执行时间、截止期限丢失、CAN 负载与数据陈旧度。
- [ ] CI 能生成 FSM 状态图/转换清单，并检测不可达状态、未处理事件和没有安全退出路径的运行状态。
- [ ] 表驱动测试覆盖每个合法转换与非法状态/事件组合；属性测试覆盖重复、乱序、丢失和超时事件序列。
- [ ] 记录的 FSM 事件流可以离线重放，并产生与在线执行一致的状态和命令输出。
- [ ] 急停事件可从任何非关机状态抢占进入安全状态，且未经显式复位不能恢复运动。
- [ ] 在 `Running`、`Degraded` 和动作等待期间分别杀死并重启 FSM，系统均先禁止运动并最终停留在 `Standby` 或 `Fault`，不会自动续跑。
- [ ] 伪造旧检查点、旧确认消息或崩溃前事件时，恢复流程不会绕过新的健康检查和显式使能。
- [ ] MCAP 文件包含解码所需的 Protobuf schema、通道元数据、双时间戳和序列号，并可按时间区间回放。
- [ ] 故障触发能够保存故障前后的图像/点云滚动窗口，并与控制及 FSM 事件使用同一时间基准关联。
- [ ] 停止记录消费、制造慢盘或填满磁盘时，实时控制无额外截止期限丢失，且记录器按优先级降级并报告数据缺口。
- [ ] 依赖与构建检查证明底层、中间层、实时控制和 FSM 均为 Rust 实现，且 `motion-rt` 不链接 Python 解释器或非 Rust 算法插件。
- [ ] 一个独立的 C++ 或 Python 示例算法能够仅依赖生成的 Protobuf 类型和 Zenoh 接口消费数据、发布结果，并在崩溃后不影响实时控制。
- [ ] 可选 ROS 2 集成测试能够映射至少一个传感器 topic、一个控制命令、一个查询/服务和一个长任务/action，并验证单位、坐标系、QoS 和错误语义。
- [ ] 杀死或断开 `ros2-bridge` 时，实时控制继续运行或按本地安全策略停止，不会因 ROS 2 故障绕过命令租约。
- [ ] 两个通过以太网连接的 ARM/开发节点能够交换 Zenoh + Protobuf 状态、命令和健康消息；断网时本地控制按租约安全降级，恢复后不会重放陈旧命令。
- [ ] 网口节点能够发布传感器数据或控制指令，并验证陈旧、乱序、重复、断线重连和时钟不同步时的拒绝/降级行为。
- [ ] 在网络延迟、丢包和断网注入期间，1 kHz 本地调度线程不发生等待；消费者仅使用有效快照并按配置进入降级或安全停止。
- [ ] 同一车体速度与 SE(2) 轨迹测试集能够在舵轮、麦克纳姆轮和全向轮运动学实现上运行，并验证各自约束与饱和行为。
- [ ] 轮速、IMU 或外部位姿分别陈旧/丢失时，状态估计和底盘控制进入明确的降级或停止状态。
- [ ] 一个示例自动项目能够仅用可复用积木表达顺序、并行、条件、超时、重试和取消，并在 FSM 的急停/故障事件下确定性终止。
- [ ] 编排器事件与动作结果可被记录、回放和单元测试，且不会绕过 FSM 的安全守卫。
- [ ] 类型化 Rust DSL 能组合并复用子流程，且编译/启动校验能够拒绝缺少取消路径、未知动作或资源冲突的任务。
- [ ] HSM 离开 `Running` 时，所有活动任务节点均被取消并产生确定的终止结果，不保留可在重新使能后自行恢复的后台动作。
- [ ] 并发发送自动任务、人工控制、ROS 2 和远程测试命令时，同一运动资源只有当前租约持有者的命令被执行。
- [ ] FSM 崩溃、租约过期、epoch 切换和人工抢占测试均能使旧命令在规定时间内失效，并进入预期停止或新控制模式。
- [ ] 达妙电机能够通过目标 ARM 板的 CAN/SocketCAN 完成发现或配置校验、使能、目标下发、反馈读取、故障上报、超时停机和显式复位。
- [ ] DM-J4310-2EC MIT 编解码具有官方协议测试向量或抓帧对照测试，并覆盖最小值、最大值、越界拒绝和故障状态。
- [ ] Orange Pi 5 Plus 能通过外接隔离式 CAN 收发器在 `can0` 或 `can1` 上以 1 Mbps 稳定控制 DM-J4310-2EC，并记录可复现的内核、设备树和接线基线。
- [ ] 从固定源码与补丁清单能够重建 Orange Pi 5 Plus 的 Ubuntu 22.04 Server + 5.10 PREEMPT_RT 内核镜像，并通过启动、CAN、网络、USB/MIPI 和实时压力检查。
- [ ] 中间层本地 IPC 在 RK3588 上对照固定 Horus 提交完成延迟、最大抖动、CPU、内存、慢消费者、溢出、撕裂和进程崩溃测试；共享内存类型必须通过显式安全契约，不能靠无析构启发式推断。

## Out of Scope for V1

- 具体机器人整机的控制器增益标定、完整机械臂动力学与视觉模型实现。
- 除 DM-J4310-2EC MIT 模式之外的具体电机协议，以及尚未选定的 IMU、相机和雷达协议实现。
- 首版生产级网络身份、mTLS 证书生命周期和 Zenoh ACL 策略。
- 底层网口设备驱动及原始以太网、通用 TCP/UDP 设备协议抽象。
- 首版虚拟设备、`vcan` 控制闭环和 Gazebo 等机器人仿真集成。
